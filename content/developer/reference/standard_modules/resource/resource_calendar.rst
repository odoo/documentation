=================
Working schedules
=================

A working schedule (`resource.calendar`) describes when work is expected. It is made of
**attendances** (`resource.calendar.attendance`), the expected work slots, and **leaves**
(`resource.calendar.leaves`), the periods interrupting them. Every resource, hence every
employee, has a calendar; each company has a default one (`res.company.resource_calendar_id`).

This page explains these three models, then the methods used to compute work intervals,
durations and dates from them.

.. seealso::
   :ref:`reference/resource/intervals` and :ref:`reference/resource/conventions`, which apply to
   every method described below.

.. _reference/resource/resource_calendar/types:

Calendar types
--------------

The `calendar_type` field determines how attendances are defined:

`fixed` (default)
   Undated attendances repeated every week on their `dayofweek` (`'0'` is Monday). This is the
   regular "Monday to Friday, 8:00-12:00 and 13:00-17:00" schedule. `hours_per_week`,
   `days_per_week` and `hours_per_day` are computed from the attendances.

`variable`
   Dated attendances (`date`), optionally recurring: `recurrency_type` (`days` or `weeks`),
   `recurrency_interval`, `recurrency_end_type` (`forever`, `times` or `date`) and the list of
   excluded occurrences. Multi-week rotations (e.g. one week out of two) are variable calendars
   with recurring attendances. `hours_per_week` and `hours_per_day` are set manually.

`undefined` (flexible)
   No attendance at all: the resource works whenever it wants, optionally within an
   `hours_per_week` and an `hours_per_day` target. When both targets are zero, the calendar is
   **fully flexible** and the resource is considered as working the whole time. See
   :ref:`reference/resource/resource_calendar/flexible`.

Switching the type of a calendar deletes the attendances that do not fit the new type.

.. _reference/resource/resource_calendar/attendances:

Attendances
-----------

An attendance is either:

- **timed**: `hour_from` and `hour_to` are set, as float hours in the local time of the resource
  (`16.5` is 16:30, `24` is the end of the day);
- **duration-based**: only `duration_hours` is set (e.g. 8 hours on Monday). When intervals are
  generated, the duration-based attendances of a day are placed one after the other, centered on
  12:00. The default calendar of a company is built this way, so its intervals are 8:00-16:00.

A day cannot mix both kinds. `day_period` (`morning`, `afternoon` or `full_day`) is computed
from the hours; it is used to request half days of time off.

.. _reference/resource/resource_calendar/leaves:

Leaves
------

A `resource.calendar.leaves` record is a period during which the calendar's attendances do not
apply:

- without `resource_id`, it is a **global leave** (typically a public holiday): it applies to
  every resource of its company using the calendar;
- with a `resource_id`, it only applies to that resource. Validated time off requests create
  such leaves.

`count_as` tells whether the leave is an `absence` (default) or counts as `working_time` (e.g. a
training). Leave methods only deduct absences by default.

`date_from` and `date_to` are datetime fields, hence naive UTC datetimes in the database.

.. _reference/resource/resource_calendar/intervals:

Computing work intervals
------------------------

Four methods generate the intervals of a calendar for a period, in batch for several resources.
They all follow the :ref:`conventions <reference/resource/conventions>` of the module.

:meth:`~ResourceCalendar._attendance_intervals_batch`
   The theoretical work intervals generated by the attendances, leaves not deducted. Each
   interval carries its attendance as payload.

:meth:`~ResourceCalendar._leave_intervals_batch`
   The leave intervals: global leaves, plus the leaves of each resource. Each interval carries
   its leaves as payload.

:meth:`~ResourceCalendar._work_intervals_batch`
   The effective work intervals: attendance intervals minus leave intervals. **This is the
   method to use** to know when resources actually work, and the one other modules override to
   alter the result (e.g. `hr_work_entry`).

:meth:`~ResourceCalendar._unavailable_intervals_batch`
   The complement of the work intervals within the period, in UTC. Used by Gantt views to grey
   out unavailable time.

`_leave_intervals` and `_unavailable_intervals` are single-resource shortcuts.

.. example::

   A 38-hour calendar (8:00-12:00 and 13:00-16:36, Monday to Friday) with a public holiday on
   Tuesday, and two resources in different timezones, `r2` being sick on Wednesday morning.

   .. code-block:: python

      from datetime import datetime
      from zoneinfo import ZoneInfo

      from odoo.fields import Command

      calendar = env['resource.calendar'].create({
          'name': 'Standard 38 hours/week',
          'attendance_ids': [Command.clear()] + [
              Command.create({'dayofweek': str(day), 'hour_from': hour_from, 'hour_to': hour_to})
              for day in range(5)
              for hour_from, hour_to in ((8, 12), (13, 16.6))
          ],
      })
      r1 = env['resource.resource'].create({
          'name': 'R1', 'calendar_id': calendar.id, 'tz': 'Asia/Kolkata',
      })
      r2 = env['resource.resource'].create({
          'name': 'R2', 'calendar_id': calendar.id, 'tz': 'Europe/Brussels',
      })
      env['resource.calendar.leaves'].create([{
          'name': 'Public holiday',  # global leave: no resource
          'calendar_id': calendar.id,
          'date_from': datetime(2026, 10, 20, 0, 0),  # naive UTC
          'date_to': datetime(2026, 10, 20, 22, 0),
      }, {
          'name': 'Sick',
          'resource_id': r2.id,
          'date_from': datetime(2026, 10, 21, 6, 0),
          'date_to': datetime(2026, 10, 21, 10, 0),
      }])

      brussels = ZoneInfo('Europe/Brussels')
      start = datetime(2026, 10, 19, tzinfo=brussels)
      end = datetime(2026, 10, 24, tzinfo=brussels)
      resources_per_tz = (r1 | r2)._get_resources_per_tz()

      attendances = calendar._attendance_intervals_batch(start, end, resources_per_tz)
      list(attendances)  # [r1.id, False, r2.id]
      next(iter(attendances[r2.id]))
      # (datetime(2026, 10, 19, 8, 0, tzinfo=ZoneInfo('Europe/Brussels')),
      #  datetime(2026, 10, 19, 12, 0, tzinfo=ZoneInfo('Europe/Brussels')),
      #  resource.calendar.attendance(...))
      next(iter(attendances[r1.id]))[0]
      # datetime(2026, 10, 19, 8, 0, tzinfo=ZoneInfo('Asia/Kolkata')): 8:00 local time

      work = calendar._work_intervals_batch(start, end, resources_per_tz)
      {
          key: sum((stop - start).total_seconds() / 3600 for start, stop, _ in intervals)
          for key, intervals in work.items()
      }
      # {r1.id: 30.4, False: 30.4, r2.id: 26.4}

.. _reference/resource/resource_calendar/durations:

Computing durations
-------------------

When only a quantity of work is needed, use:

:meth:`~ResourceCalendar.get_work_hours_count`
   The number of calendar-level work hours between two dates or datetimes. Only global leaves
   are deducted (no resource).

:meth:`~ResourceCalendar.get_work_duration_data`
   The calendar-level work duration as `{'days': float, 'hours': float}`.

:meth:`~ResourceCalendar._get_attendance_intervals_days_data`
   Converts any work intervals into `{'days': float, 'hours': float}`. A day counts for half a
   day if its hours are at most 3/4 of the reference hours of that day, otherwise for a full day.

For a specific resource or employee, use the methods of
:ref:`resource.mixin <reference/resource/resource_resource>` instead, which also deduct the
leaves of the resource.

.. example::

   With the calendar of the previous example:

   .. code-block:: python

      calendar.get_work_hours_count(start, end)                        # 30.4
      calendar.get_work_hours_count(start, end, compute_leaves=False)  # 38.0
      calendar.get_work_duration_data(start, end)  # {'days': 4.0, 'hours': 30.4}

.. important::
   With timezone-aware datetimes, `get_work_hours_count` reads the attendance hours in the
   timezone of the given datetimes. Passing UTC datetimes to compute the hours of a Brussels
   calendar reads 8:00-12:00 as 8:00-12:00 UTC. Pass datetimes in the right timezone, or dates
   (interpreted in the company's timezone).

.. _reference/resource/resource_calendar/planning:

Planning and dates
------------------

:meth:`~ResourceCalendar.plan_hours`
   Returns the datetime at which a given number of work hours, starting from a datetime, ends
   (or starts, with a negative number of hours). The computation happens in the timezone of the
   given `resource`, or of the company without resource.

:meth:`~ResourceCalendar.plan_days`
   Same, with a number of working days. It returns the end of the *first attendance* of the
   last day (e.g. 12:00 for a schedule with a lunch break), not the end of that day.

:meth:`~ResourceCalendar._get_closest_work_time`
   Returns the work interval start (or end) closest to a datetime, e.g. to snap a datetime
   typed by a user to the working hours.

:meth:`~ResourceCalendar._works_on_date` and :meth:`~ResourceCalendar._get_attendances_by_date`
   Tell whether the calendar has attendances on a date, and which ones, taking recurrences of
   variable calendars into account.

:meth:`~ResourceCalendar._get_unusual_days`
   Returns `{'YYYY-MM-DD': bool}`, `True` for days without work (weekends, public holidays).
   Calendar widgets use it to grey out days.

.. example::

   .. code-block:: python

      monday_9am = datetime(2026, 10, 19, 9, 0, tzinfo=brussels)
      calendar.plan_hours(10, monday_9am, resource=r2)
      # datetime(2026, 10, 20, 11, 24, tzinfo=ZoneInfo('Europe/Brussels'))
      # with compute_leaves, the public holiday and the sick leave of r2 are skipped
      calendar.plan_hours(10, monday_9am, compute_leaves=True, resource=r2)
      # datetime(2026, 10, 21, 16, 24, tzinfo=ZoneInfo('Europe/Brussels'))
      calendar.plan_hours(2, datetime(2026, 10, 19, 9, 0), resource=r2)  # naive = UTC
      # datetime(2026, 10, 19, 12, 0): 11:00 to 14:00 in Brussels, lunch break excluded

      calendar._get_unusual_days(start, end)
      # {'2026-10-19': False, '2026-10-20': True, '2026-10-21': False, '2026-10-22': False,
      #  '2026-10-23': False, '2026-10-24': True}

.. _reference/resource/resource_calendar/flexible:

Flexible calendars
------------------

A flexible calendar (`calendar_type = 'undefined'`, see
:meth:`~ResourceCalendar._is_flexible`) has no
attendance, so the interval methods generate synthetic ones for the resources using it:

- **fully flexible** (no hours target): a single interval covering the whole period;
- **with targets**: one interval per day, of at most `hours_per_day` hours centered on 12:00,
  until `hours_per_week` is reached. Weeks are counted in blocks of 7 days starting at
  `start_dt`, not in calendar weeks.

Leaves of a flexible resource are extended to whole days.

.. note::
   Whether a resource is flexible is decided from **its own calendar** at the start of the period
   (or the calendar of its employee's version, with `hr`), not from the calendar the method is
   called on.

.. example::

   .. code-block:: python

      flexible = env['resource.calendar'].create({
          'name': 'Flexible 20 hours/week',
          'calendar_type': 'undefined',
          'hours_per_week': 20,
          'hours_per_day': 6,
      })
      flexible.get_work_duration_data(
          datetime(2026, 10, 19, tzinfo=brussels), datetime(2026, 10, 26, tzinfo=brussels),
      )
      # {'days': 3.5, 'hours': 20.0}: 6 hours from Monday to Wednesday, 2 hours on Thursday

.. _reference/resource/resource_calendar/pitfalls:

Pitfalls
--------

- Interval methods raise an assertion error with naive datetimes. Localize them first, e.g.
  `datetime(2026, 10, 19, tzinfo=ZoneInfo(resource.tz))`.
- Calendar-level results (the `False` key, `get_work_hours_count`, ...) only deduct **global**
  leaves. Use a resource to also take its own time off into account.
- `domain=None` and `domain=[]` differ in leave methods: the first one only deducts absences,
  the second one also deducts leaves counted as working time. Domains must be lists.
- In `get_work_duration_data`, `domain` filters the leaves when `compute_leaves` is set, and the
  attendances otherwise.
- The payload of the intervals of a flexible calendar is a new, unsaved attendance holding only
  `duration_hours`: do not rely on its `id` or `calendar_id`.
- Do not mutate the returned `Intervals`: the same object can be shared by several resources.

.. _reference/resource/resource_calendar/extending:

Extending
---------

The following methods are designed to be overridden:

- :meth:`~ResourceCalendar._work_intervals_batch`
  to alter the effective work intervals;
- :meth:`~ResourceCalendar._get_reference_hours_per_day`
  to change the number of hours making a full day when converting hours to days;
- :meth:`~ResourceCalendar._handle_flexible_leave_interval`
  to change how the leaves of flexible resources are stretched;
- `resource.calendar.attendance._is_work_period` to exclude some attendances from the work
  time (`hr_work_entry` excludes the attendances whose work entry type counts as an absence).
